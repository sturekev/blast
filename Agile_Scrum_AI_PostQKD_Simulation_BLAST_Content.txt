2. PROBLEM / MOTIVATION
================================================================================

THE PROBLEM IN ONE SENTENCE:
Student research on emerging network technologies routinely fails not because
the science is too hard, but because the WORK PROCESS is undisciplined — a
single giant build attempted at the end of the semester, no intermediate
working version, no tests, no record of what was verified versus what was
assumed, and increasingly, AI-generated content accepted without validation.

WHY THIS IS A REAL ENGINEERING PROBLEM, NOT A STUDY-HABITS COMPLAINT:

  (a) THE REQUIREMENTS GENUINELY CHANGE MID-PROJECT.
      Post-QKD is a moving target. Standards evolve, algorithm names change
      (the Open Quantum Safe Docker image renamed `kyber768` to `mlkem768`
      between versions to reflect FIPS 203 finalization, breaking scripts
      written against the older name) [8]. A plan-driven process that fixes
      all requirements up front is structurally mismatched to this domain.
      Your own course material states the principle directly: "Plan-driven
      processes are processes where all of the process activities are planned
      in advance and progress is measured against this plan. In agile
      processes, planning is incremental and it is easier to change the
      process to reflect changing customer requirements" [1].

  (b) A SOLO STUDENT HAS NO SAFETY NET.
      There is no QA team, no code reviewer, no integration engineer. Process
      must substitute for personnel. Scrum's inspect-and-adapt events and a
      hard Definition of Done are the cheapest available replacements.

  (c) SIMULATION SOFTWARE CAN BE CONFIDENTLY WRONG.
      A QKD simulator that silently produces a key is indistinguishable, from
      the outside, from one that produces a CORRECT key. Unlike a web app,
      there is no visible crash when the cryptography is subtly broken. This
      makes TEST ORACLE DESIGN — not coding — the hardest part of the project.

  (d) AI ASSISTANCE INTRODUCES A NEW FAILURE MODE.
      Generative models produce plausible, well-formatted, incorrect
      citations and plausible, well-formatted, incorrect code. The course
      research expectations are explicit: "Do not base the project primarily
      on Wikipedia, random blogs, social-media posts, marketing pages, or
      AI-generated summaries," and "AI tools may assist only according to
      course policy and do not replace scholarly or authoritative sources"
      [2]. A defensible process must therefore include an explicit
      AI-verification gate, not an informal intention to "check later."

MOTIVATING QUESTION DRIVING THIS WORK:
  "What is the smallest disciplined process that lets one student produce a
   post-QKD simulation that is demonstrably correct, incrementally delivered,
   reproducible by a third party, and honest about which parts are verified
   versus assumed?"

3. BACKGROUND — MINIMUM CONCEPTS A READER NEEDS
================================================================================

B1. SOFTWARE PROCESS MODEL — AND WHY THERE IS NO "RIGHT" ONE
    A software process model is an abstract description of how development
    work is organized: what activities occur, in what order, and how progress
    is judged. The foundational position in your course material is worth
    quoting because it prevents a common poster mistake (declaring Agile
    "better" than Waterfall): "In practice, most practical processes include
    elements of both plan-driven and agile approaches. There are no right or
    wrong software processes" [1].

B2. THE FIVE APPROACHES FROM BLA_02 (condensed)
    - WATERFALL. Sequential, linear: Requirements -> Design -> Implementation
      -> Testing -> Maintenance. Each phase completed fully before the next.
      Suited to large projects with fixed, well-understood requirements,
      strict regulatory compliance, or safety criticality (aerospace, medical
      equipment, infrastructure) [1].
    - INCREMENTAL DEVELOPMENT. The system is built in small, manageable
      pieces, each adding capability to a working whole [1].
    - INTEGRATION AND CONFIGURATION. The system is assembled largely from
      existing, reusable components rather than written from scratch [1].
    - PLAN-DRIVEN DEVELOPMENT. All activities planned in advance; progress
      measured against the plan [1].
    - AGILE DEVELOPMENT. Iterative and human-centered: continuous delivery,
      flexibility, customer collaboration, rapid response to changing
      requirements. "Work progresses through short, time-boxed iterations
      (sprints) resulting in working software increments." Appropriate for
      startups, innovative products with changing requirements, customer-
      facing applications, or teams needing rapid adaptation from frequent
      feedback [1].

B3. INCREMENT (the precise meaning — commonly misused)
    An INCREMENT is not "a chunk of work finished." Under Scrum, an Increment
    is a concrete stepping stone toward the Product Goal; each Increment is
    ADDITIVE to all prior Increments, must be thoroughly verified to ensure
    all Increments work together, and must be USABLE. Critically, work cannot
    be considered part of an Increment unless it meets the Definition of Done
    [3]. An increment that does not run is not an increment — it is
    work-in-progress.

B4. SCRUM — THE FRAMEWORK IN ITS OWN TERMS
    Scrum is a lightweight framework built on empiricism (transparency,
    inspection, adaptation) with:
      - THREE ACCOUNTABILITIES: Product Owner (maximizes product value and
        owns the Product Backlog), Scrum Master (establishes Scrum, coaches,
        removes impediments), Developers (create a usable Increment each
        Sprint).
      - FIVE EVENTS: the Sprint (the container, a fixed period of one month
        or less), Sprint Planning, Daily Scrum, Sprint Review, Sprint
        Retrospective.
      - THREE ARTIFACTS, each with a commitment: Product Backlog (commitment:
        Product Goal), Sprint Backlog (commitment: Sprint Goal), Increment
        (commitment: Definition of Done) [3].
    SOLO ADAPTATION NOTE FOR THE POSTER: a one-student project cannot
    populate three accountabilities with three people. State plainly that you
    hold all three roles and that the risk this creates — no independent
    challenge to your own decisions — is mitigated by (i) a written
    Definition of Done you cannot silently relax, (ii) automated CI as an
    impartial gatekeeper, and (iii) faculty sponsor review at Sprint Review.
    Describing this honestly is stronger than claiming you "ran Scrum."

B5. VERIFICATION VS. VALIDATION (the distinction graders look for)
    - VERIFICATION: "Are we building the product right?" Does the code match
      its specification? (unit tests, property tests, static analysis)
    - VALIDATION: "Are we building the right product?" Does the simulation
      actually represent BB84 and hybrid key derivation as the literature
      describes them? (comparison against analytical bounds and published
      protocol behavior)
    A simulator can pass 100% of its unit tests and still be an invalid model
    of QKD. Both are required.

B6. TEST ORACLE
    An oracle is the mechanism that decides whether an observed output is
    correct. In ordinary software the oracle is obvious. In a stochastic
    quantum-network simulation it is NOT, because every run differs. Section
    6 and Section 9 describe the three oracle types this project uses:
    analytical bounds, metamorphic relations, and cross-implementation
    differential testing.

B7. WHAT "POST-QKD" MEANS HERE (carried over from the companion poster)
    The hybrid architecture in which QKD supplies information-theoretic key
    material on specific high-value links while PQC supplies scalable
    authentication and an independent second key-agreement path, with the
    final session key derived from BOTH so the system survives failure of
    either. Your attached QKD reference identifies hybrid QKD+PQC — "such as
    lattice-based cryptographic algorithms" — as "gaining traction as a
    practical approach for robust security," rates the authentication gap as
    MEDIUM severity, and gives a resolution timeline of "Short term (1–3
    years) for hybrid solutions; longer term (5–10 years) for full reliance
    on quantum-based authentication technologies like QDS and QSIs" [4].

LAYER B — QUANTUM NETWORK SIMULATION ENGINE (choose ONE; justify the choice)
  Verified, real, actively used options:
  - NetSquid — discrete-event simulator for quantum networks with detailed
    physical modeling; supports hardware imperfections, photon loss, and
    decoherence; designed for scale [11][12].
  - SeQUeNCe — customizable discrete-event simulator of quantum networks,
    open-source, modular design with cross-module communication [13].
  - QuNetSim — focuses on simplifying development and implementation of

  - SimulaQron — distributed simulation whose main purpose is application

    accurately tracks time [12].

  VERSUS LOSS, you need physical-layer realism and timing, which points to
  NetSquid or SeQUeNCe. If your research question is about PROTOCOL LOGIC and
  the key-delivery API, QuNetSim's higher abstraction is sufficient and
  faster to learn. State your choice and this reasoning on the poster — the
  rubric rewards justified technical decisions.

LAYER C — POST-QUANTUM CRYPTOGRAPHY LIBRARY
  Open Quantum Safe (OQS): liboqs, an open-source C library of quantum-

LAYER D — QUANTUM PROGRAMMING FRAMEWORKS (for any circuit-level component)

6. HOW IT WORKS — THE PROCESS MECHANISM AND WORKFLOW
================================================================================

This is a workflow, not a glossary. Phases 1–6 describe one full cycle; the
cycle repeats every sprint.

--------------------------------------------------------------------------------
PHASE 1 — PRODUCT GOAL AND INITIAL PRODUCT BACKLOG (once, before Sprint 1)
--------------------------------------------------------------------------------
PRODUCT GOAL (the commitment the Product Backlog serves):
  "A reproducible simulation that measures secret-key rate and QBER for a
   BB84 link, delivers keys through an ETSI-style REST interface, derives a
   hybrid session key combining QKD-sourced and ML-KEM-sourced secrets, and
   reports which of its behaviors are verified against analytical bounds."

INITIAL PRODUCT BACKLOG (ordered; each item written as a testable outcome):
  P1  Simulate BB84 over a lossless channel and produce a sifted key.
  P2  Confirm sifting ratio converges to the expected ~1/2 for random
      independent basis choices.
  P3  Add configurable channel loss; measure raw key rate versus loss.
  P4  Add a noise model; measure QBER; confirm QBER responds to the noise
      parameter monotonically.
  P5  Add an intercept-resend eavesdropper; confirm QBER rises measurably
      when the eavesdropper is active.
  P6  Implement error reconciliation; confirm both endpoints hold identical
      strings afterward.
  P7  Implement privacy amplification; confirm output length shrinks as QBER
      rises and reaches zero above the protocol's security threshold.
  P8  Expose keys through a local REST endpoint matching the ETSI GS QKD 014
      shapes (status, enc_keys, dec_keys; JSON key container with key_ID).
  P9  Implement key-pool exhaustion behavior returning the correct HTTP
      error rather than reusing key material.
  P10 Integrate liboqs ML-KEM and derive a hybrid session key from QKD key
      material plus the ML-KEM shared secret.
  P11 Confirm the hybrid property: changing ANY single contributing secret
      changes the final session key.
  P12 Produce reproducible result figures tagged with seed and commit hash.

NOTE ON BACKLOG ORDERING: items are ordered so that EVERY prefix of the list
is a working system. That ordering decision is what makes the project
incremental rather than merely chunked.

PHASE 2 — SPRINT PLANNING (start of each sprint)
--------------------------------------------------------------------------------
Three questions, answered in writing and committed to the repository:
  (a) WHY is this Sprint valuable? -> one-sentence SPRINT GOAL.
  (b) WHAT can be Done this Sprint? -> selected Product Backlog items.
  (c) HOW will the work get done? -> the plan, which together with (a) and

SOLO DISCIPLINE RULE: the Sprint Goal is written BEFORE any code is opened,
and is not edited mid-sprint. If it turns out to be wrong, that becomes a
Retrospective finding — which is data — rather than a silent rewrite, which
is self-deception.

PHASE 4 — BUILDING THE INCREMENT, UNDER THE DEFINITION OF DONE
--------------------------------------------------------------------------------
DEFINITION OF DONE (copy this verbatim into the repository as DoD.md; an item

  [ ] Code runs end-to-end from a single documented command.
  [ ] Unit tests exist for every new public function.
  [ ] At least one PROPERTY or METAMORPHIC test exists for every new
      probabilistic behavior.
  [ ] Any analytically predictable behavior is asserted against its
      analytical value, not against a hard-coded output captured from a
      previous run.
  [ ] Full test suite passes in CI on a clean checkout.
  [ ] The RNG seed is explicit and recorded; the run is reproducible.
  [ ] Dependency versions are pinned.
  [ ] Any AI-assisted content is marked in the commit message and has passed
      the Phase 5 verification gate.
  [ ] Every factual claim added to documentation carries a citation to a
      primary source, not to an AI summary [2].
  [ ] README updated so a stranger can reproduce the result.

WHY THE DoD IS THE LOAD-BEARING ARTIFACT HERE: in a solo project with AI
assistance, it is trivially easy to generate 400 lines of plausible code in
two minutes and feel productive. The DoD is the only mechanism that converts
"generated" into "delivered."

9. QUALITY CONTROL AND TESTING — THE TECHNICAL CORE
================================================================================

This section exists because the hardest problem in simulating a stochastic
security protocol is not writing it — it is KNOWING WHETHER IT IS RIGHT.

--------------------------------------------------------------------------------
9.1 THE ORACLE PROBLEM, STATED PLAINLY
--------------------------------------------------------------------------------
Every run of a BB84 simulation produces a DIFFERENT key. You cannot assert
`assert key == expected_key`. Comparing against a previously saved output is
also invalid, because it only proves the code still does what it did before —
including, if it was wrong, continuing to be wrong. Three oracle strategies
solve this.

--------------------------------------------------------------------------------
9.2 ORACLE TYPE 1 — ANALYTICAL BOUNDS (strongest; use wherever possible)
--------------------------------------------------------------------------------
Assert against values that THEORY predicts, independent of your code.

 PROPERTY                      | ANALYTICAL EXPECTATION      | TEST FORM
 ------------------------------|-----------------------------|---------------
 Sifting ratio (BB84, two      | ~1/2 of detected events     | statistical
 randomly and independently    | survive basis matching      | assertion over
 chosen bases)                 |                             | many trials
 ------------------------------|-----------------------------|---------------
 QBER on a noiseless, Eve-free | ~0                          | tight bound
 channel                       |                             |
 ------------------------------|-----------------------------|---------------
 QBER with intercept-resend    | must rise MEASURABLY and    | comparative
 eavesdropper active           | significantly above the     | assertion vs.
                               | no-Eve baseline             | control run
 ------------------------------|-----------------------------|---------------
 Final key length vs. QBER     | monotonically decreasing;   | monotonicity
                               | reaches zero at/above the   | test + cutoff
                               | protocol's security         | test
                               | threshold                   |
 ------------------------------|-----------------------------|---------------
 Key agreement after           | endpoints identical,        | exact equality
 reconciliation                | bit-for-bit                 | assertion

 <<VERIFY before printing any specific numeric QBER threshold: cite the
   security-analysis source you actually read and quote its stated
   assumptions (protocol variant, one-way vs. two-way reconciliation,
   asymptotic vs. finite-key regime). Do NOT print a bare percentage with no
   stated regime — that is the kind of unsupported claim the rubric's
   "Emerging Technology Research & Technical Accuracy" criterion penalizes.>>

STATISTICAL TESTING DISCIPLINE: because these are stochastic quantities, each
assertion must specify sample size and tolerance, and tests must use a FIXED
SEED so failures are reproducible. A flaky test is worse than no test — it
trains you to ignore red builds.

--------------------------------------------------------------------------------
9.3 ORACLE TYPE 2 — METAMORPHIC TESTING (for when no absolute value is known)
--------------------------------------------------------------------------------
Metamorphic testing asserts RELATIONS BETWEEN RUNS rather than absolute
outputs. This is the key technique for simulation validation.

 METAMORPHIC RELATION (MR)                               | WHY IT MUST HOLD
 --------------------------------------------------------|------------------
 MR1: increase channel loss -> secret key rate must not   | Physics: fewer
      increase                                            | detections
 --------------------------------------------------------|------------------
 MR2: increase noise parameter -> QBER must not decrease  | Definition of
                                                          | noise
 --------------------------------------------------------|------------------
 MR3: enable eavesdropper -> QBER must not decrease       | Measurement
                                                          | disturbance
 --------------------------------------------------------|------------------
 MR4: double the number of transmitted pulses -> raw key  | Linearity in
      length approximately doubles (same parameters)      | trial count
 --------------------------------------------------------|------------------
 MR5: same seed + same parameters -> byte-identical       | Determinism
      output                                              | under seeding
 --------------------------------------------------------|------------------
 MR6: different seed, same parameters -> different key,   | Correct use of
      same statistical behavior                           | randomness
 --------------------------------------------------------|------------------
 MR7 (HYBRID / POST-QKD): change ONLY the QKD key input   | Hybrid security
      -> session key changes. Change ONLY the ML-KEM      | property: the
      secret -> session key changes. This is the          | session key must
      executable form of the defense-in-depth claim.      | depend on BOTH

MR7 IS THE MOST IMPORTANT TEST IN THE ENTIRE PROJECT. It is the difference
between claiming a hybrid design and demonstrating one. Put it on the poster.

--------------------------------------------------------------------------------
9.4 ORACLE TYPE 3 — DIFFERENTIAL / CROSS-IMPLEMENTATION TESTING
--------------------------------------------------------------------------------
Where a reference implementation exists, compare against it rather than
trusting your own. liboqs explicitly provides "a test harness and benchmarking
routines" alongside its algorithm implementations [6] — use them. For the
PQC portion, your code should never be the authority on correctness; the
maintained library is.
LIMITATION TO STATE HONESTLY: for the QKD portion there is no single
authoritative reference implementation to diff against, which is precisely
why Oracle Types 1 and 2 carry the load there — and why the community notes a
"lack of validation methods for existing quantum network simulations" [12].

--------------------------------------------------------------------------------
9.5 THE TEST PYRAMID AS APPLIED HERE
--------------------------------------------------------------------------------
        /\          L8  REPRODUCIBILITY   (1 test: clean checkout -> same fig)
       /  \         L7  STATISTICAL       (few: randomness of output keys)
      /    \        L6  END-TO-END        (few: full key establishment)
     /      \       L5  INTEGRATION       (some: REST contract, pool states)
    /        \      L4  METAMORPHIC       (many: MR1-MR7)
   /          \     L3  PROPERTY          (many: invariants, Hypothesis)
  /____________\    L2  UNIT              (most: every public function)
                    L1  STATIC            (always: lint + types, pre-commit)

RATIONALE: the unusual feature of this pyramid is how WIDE the metamorphic
band is. In ordinary application software that band barely exists. In
stochastic scientific software it does most of the real validation work.

--------------------------------------------------------------------------------
9.6 CONTINUOUS INTEGRATION AS THE ENFORCER
--------------------------------------------------------------------------------
GitHub Actions runs L1–L6 on every push and L7–L8 nightly or per release tag.
WHY THIS MATTERS SPECIFICALLY FOR A SOLO SCRUM PROJECT: the Definition of Done
is a promise you make to yourself, and promises made to oneself under deadline
pressure are not reliable. CI converts the DoD from an intention into a gate
that cannot be bypassed without a visible, recorded act.

10. BENEFITS
================================================================================

B1. A WORKING SYSTEM EXISTS FROM SPRINT 1 ONWARD.
    Because the backlog is ordered so that every prefix runs, the project is
    never in a state of "nothing to show." WHY IT MATTERS: it eliminates the
    dominant failure mode of semester research projects — an all-or-nothing
    integration at the deadline. It also means a demo is always possible at
    Sprint Review, which is what Scrum requires of an Increment: usable, and
    additive to all prior Increments [3].

B2. CORRECTNESS IS MEASURED, NOT ASSUMED.
    Analytical and metamorphic oracles mean the simulator's claims are
    checkable by a third party. WHY IT MATTERS: the poster can state which
    behaviors are VERIFIED and which are merely IMPLEMENTED — a distinction
    almost no student poster makes, and one the critical-thinking standard
    explicitly asks for in the form "WHAT evidence supports the claim?" [2].

B3. CHANGE IS ABSORBED INSTEAD OF DERAILING THE PROJECT.
    When an upstream tool renames algorithms mid-project [8], an incremental
    process reorders the backlog and continues. A plan-driven schedule would
    have to be rewritten. WHY IT MATTERS: this domain changes faster than a
    semester, so adaptability is a functional requirement, not a preference.

B4. AI ACCELERATES THE PROJECT WITHOUT CONTAMINATING IT.
    Bounding AI to four advisory tasks behind a verification gate captures the
    speed benefit — faster literature triage, more edge cases considered —
    while keeping the authoritative content sourced from ETSI, IETF, NIST, and
    IEEE material, as course policy requires [2]. WHY IT MATTERS: it is a
    reusable answer to "how should students use AI in research," stated as a
    process rather than as a vague ethic.

B5. REUSE BEATS REIMPLEMENTATION FOR CRYPTOGRAPHY.
    Using liboqs rather than hand-rolling ML-KEM yields a maintained, tested,
    standardized implementation with its own test harness [5][6]. WHY IT
    MATTERS: student-written cryptography is a known source of subtle,
    invisible error. Choosing not to write it is an engineering judgment worth
    defending aloud.

B6. THE PROCESS PRODUCES ITS OWN EVIDENCE.
    Sprint logs, tagged releases, CI history, the AI usage log, and the
    reproducibility pack are generated as a BY-PRODUCT of working correctly.
    WHY IT MATTERS: they directly satisfy the GitHub repository and
    professional-integration requirements, which call for the poster,
    abstract, diagrams, references, and appropriate project artifacts [2].

B7. TRANSFERABILITY.
    Nothing in this process is specific to QKD. The same structure applies to
    any simulation-based networking research where hardware is unavailable.
    WHY IT MATTERS: it elevates the poster from "I built a thing" to "here is
    a method others can adopt," which is what "From Building to Innovation"
    asks for.

11. LIMITATIONS / CHALLENGES
================================================================================

L1. SCRUM WITH ONE PERSON IS NOT SCRUM.
    Scrum defines three accountabilities and relies on multiple people
    inspecting and challenging each other [3]. A solo student holding all
    three roles loses the independent-challenge function entirely. Automated
    CI and sponsor review are partial substitutes, not equivalents. STATE
    THIS EXPLICITLY — claiming full Scrum fidelity solo is the most likely
    technical inaccuracy on a poster of this type.

L2. PROCESS OVERHEAD IS REAL AND MEASURABLE.
    Writing sprint goals, maintaining logs, building tests, and verifying AI
    output consumes time that is not spent producing features. For very small
    or very short projects the overhead may exceed the benefit. Report your
    actual overhead honestly: <<YOUR DATA — estimated % of total hours spent
    on process artifacts vs. implementation>>.

L3. A VALIDATED SIMULATION IS STILL NOT HARDWARE.
    Passing every test means the model behaves as the model should. It does
    not mean the model matches a real optical link. Simulators differ sharply
    in realism: SimulaQron does not aim at realistic physical models of
    channels and devices; QuNetSim focuses on upper layers and leaves the
    physical layer unspecified; SQUANCH offers configurable physical-layer
    error models but does not accurately track time [12][13]. Whichever you
    choose, its abstractions bound your conclusions. Name the specific
    limitation of YOUR chosen simulator on the poster.

L4. THE ORACLE PROBLEM IS ONLY MITIGATED, NOT SOLVED.
    Metamorphic relations catch broken relationships but can miss a model that
    is uniformly, consistently wrong in the same direction. If your noise
    model is physically misspecified, MR1–MR6 may all pass. The honest claim
    is "internally consistent and consistent with known analytical bounds,"
    not "correct."

L5. NO INDEPENDENT CODE REVIEW.
    AI review is not peer review. It has no stake, no accountability, and no
    memory of your design intent. It generates plausible criticism, including
    plausible WRONG criticism — which is precisely why the process converts
    every criticism into a test rather than into a code change.

L6. AI VERIFICATION IS LABOR-INTENSIVE AND EASY TO SKIP UNDER DEADLINE.
    The gate only works if it is actually applied. Its weakest moment is the
    last week of the semester. The mitigation is structural: CI blocks merges,
    and the DoD requires the AI log entry — but a determined student can
    bypass their own rules. Acknowledge this honestly.

L7. TOOLCHAIN FRAGILITY AND VERSION DRIFT.
    Specialized research tooling breaks. Algorithm naming changes across
    releases are a documented, concrete instance [8]. Pinning by digest
    mitigates but does not eliminate this; it also means you may be running a
    version with known fixed bugs.

L8. LEARNING CURVE COST.
    Quantum network simulators and quantum programming frameworks are not
    beginner tools. The textbook notes Cirq's "steeper learning curve," that
    it is "less beginner-friendly than Qiskit," and that it has "limited
    high-level algorithm libraries" and "hardware-specific abstractions
    [that] reduce portability" [14]. Tool selection is therefore partly a
    schedule-risk decision, not purely a technical one.

L9. SCOPE CREEP IS THE NATIVE DISEASE OF INTERESTING PROJECTS.
    Post-QKD research constantly suggests a next feature — MDI-QKD, decoy
    states, trusted-node chains, satellite links. The time-box is the only
    defense, and it works only if the Sprint Goal is treated as fixed.

L10. GENERALIZABILITY OF THE PROCESS CLAIM IS UNPROVEN.
    A single-student, single-semester, single-project experience is an
    existence proof, not evidence of general effectiveness. Do not claim this
    process is better than alternatives — claim that it was applied, and
    report what it produced.

13. FUTURE IMPACT (5–15 YEARS)
================================================================================

NEAR TERM (1–3 YEARS) — AI-assisted engineering becomes governed, not banned.
  Expect institutions to move from informal AI policies to explicit,
  auditable protocols resembling the verification gate in Section 6: logged
  usage, mandatory source verification, AI excluded from authoritative
  content. The existence of a standards part addressing testing of AI-based
  systems [9] signals that formalization is already underway. For students,
  the practical consequence is that AI USAGE LOGS become as ordinary a
  deliverable as a bibliography. In parallel, hybrid QKD+PQC itself is
  expected to mature on a short-term horizon of 1–3 years [4], meaning the
  subject matter of this simulation will move from research into early
  engineering within a typical degree program's span.

MID TERM (3–7 YEARS) — simulation validation becomes a discipline.
  As quantum networking moves from physics demonstration to engineering,
  the question "is your simulator right?" will require a standardized
  answer. Plausible developments: shared benchmark scenarios with published
  reference outputs, cross-simulator differential testing as a norm, and
  reproducibility packs expected with published results. The current state —
  where simulator comparisons become "quickly obsolete" because features
  change daily [13] — is unsustainable for engineering use and will be
  pressured toward stability. The metamorphic-testing approach in Section 9
  is a plausible component of such a methodology because it does not require
  a reference implementation.

LONGER TERM (7–15 YEARS) — the process, not the product, is the durable part.
  The specific simulators, libraries, and model versions used in this project
  will be obsolete. What will not be obsolete: ordering work so every prefix
  runs, defining Done before starting, asserting against theory rather than
  against saved output, separating advisory tools from authoritative sources,
  and recording enough state that a stranger can reproduce a figure. If
  quantum repeaters mature and end-to-end QKD becomes practical, the
  simulation targets change completely — and this process still applies
  unchanged. That transferability is the actual contribution.

WHAT THIS MEANS FOR A STUDENT'S CAREER:
  The differentiating professional skill in an AI-saturated field is not
  producing output — models do that instantly — but VERIFYING output and
  being able to show how it was verified. The artifacts this process
  generates (test suites, reproducibility packs, verification logs) are
  exactly the evidence that demonstrates that skill to an employer.

14. CONCLUSION
================================================================================

MOST IMPORTANT FINDING:
For simulation-based research into emerging network technologies, the binding
constraint on the quality of the knowledge produced is the quality of the
SOFTWARE PROCESS — specifically, whether the work is ordered so that
something always runs, and whether a real test oracle exists. Applying
incremental development with time-boxed sprints produced a demonstrable
working system at every stage; applying analytical and metamorphic oracles
produced claims that a third party can check. Neither required new technology.
Both required discipline, written down in advance.

SECOND FINDING — ON PROCESS SELECTION:
This project is a hybrid process, not an Agile one, and that is the correct
outcome rather than a compromise. The external standards boundary is
plan-driven because ETSI's specification is fixed [7]; the simulator core is
incremental because its requirements are discovered by running it; the
toolchain is integration-and-configuration because reimplementing
standardized cryptography would be slower and less trustworthy [5][6]. This
is exactly what the course material predicts: "most practical processes
include elements of both plan-driven and agile approaches. There are no right
or wrong software processes" [1].

THIRD FINDING — ON AI:
AI is a legitimate and genuinely useful research instrument when it is
confined to advisory roles behind a verification gate, and a liability
otherwise. The operational rule that makes the difference is simple and worth
stating as the poster's closing line: AI MAY PROPOSE; ONLY A TEST OR A
PRIMARY SOURCE MAY CONFIRM. Under that rule, a rejected AI suggestion is not
wasted effort — it is the evidence that verification is actually happening.

THE PRACTICAL TAKEAWAY:
Build in increments that run. Define Done before you start. Assert against
theory, never against yesterday's output. Keep AI outside the repository
boundary. Record enough that a stranger can reproduce your figure. These five
rules cost little, require no special tooling, and are the difference between
a research artifact that can be defended and one that merely looks finished.

APPENDIX A — SUGGESTED POSTER ABSTRACT (for the required .docx)
================================================================================
Word count: ~220. Adjust to the instructor's limit.

Research into emerging network security technologies increasingly depends on
simulation, because the underlying hardware is costly or unavailable. The
quality of such research therefore depends directly on the quality of the
software process behind the simulation. This project applies incremental
development and the Scrum framework, together with a controlled protocol for
AI assistance, to build and validate a simulation of hybrid post-quantum
secure key establishment combining Quantum Key Distribution with
NIST-standardized post-quantum cryptography. Work is ordered so that every
stage produces a running system: BB84 over an ideal channel, then channel
loss and quantum bit error rate, then eavesdropper detection, then
reconciliation and privacy amplification, then an ETSI-style REST key
delivery interface, and finally a hybrid session key derived from both
quantum-sourced and ML-KEM-sourced secrets. The central technical challenge
is the test oracle problem: a stochastic security simulation produces
different output every run, so correctness cannot be asserted by comparison
with a saved result. The project addresses this with three oracle types —
analytical bounds from protocol theory, metamorphic relations between runs,
and differential comparison against maintained reference implementations —
enforced by continuous integration under an explicit Definition of Done. AI
models are confined to advisory roles behind a verification gate and are
never cited as sources. The contribution is a transferable, auditable process
for producing simulation-based networking research whose claims a third party
can independently reproduce and check.
